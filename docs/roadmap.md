# 路线：从 Blog as Workbase 到个人 AI 控制中心

> 这不是 v0.1.1。v0.1.1 只验证、只打磨，见 [`v0.1.1.md`](v0.1.1.md)。  
> 本文回答：MCP 是不是中间态？博客和基座要不要切？控制中心长什么样？

---

## 1. MCP 不是中间态，契合度不够是用法问题

当前形态：

```text
宿主（MiniMax Code / 以后任意 Agent 运行时）
    │  会话、模型、工具循环
    ▼
MCP（本仓库 server/mcp）
    │  20 个工具 + agent_prompt
    ▼
Vault（D:/Data/工作台）
    │  知识 / skill / context / 项目卡
    ▼
公开博客（可选展示）
```

MCP 做的是 **跨宿主的记忆与写入协议**：换 Cursor、换 DSH、换自写 runner，Vault 还在。DSH「一切皆插件」只是再包一层会话，**记忆层没有变高**。契合度不够，是因为：

- 操作环没把「id 从 list 来」写死（已在改）
- 热度、Proposal 写盘等主路径没走熟
- 没有「控制中心」把 Inbox / 焦点 / 多会话收成一块人能看见的板

这些修的是 **基座怎么被用**，不是换协议。下一阶段仍 MCP。换协议的条件只有一个：现有 20 个工具表达不了「记忆读写 + HITL 写入」。现在还表达得了。

---

## 2. 个人 AI 工作台 = 控制中心，不是更多工具

控制中心要解决的是 **人怎么指挥、Agent 怎么续上、记忆怎么进化**，不是再注册 20 个 tool。

三块，顺序不能反：

| 块 | 现在 | 以后（基座仍是 MCP + Vault） |
|---|---|---|
| **指挥板** | Inbox 看板，人拖状态 | 人只写目标 / 优先级；Agent **被宿主叫醒**后 `inbox.list` 拉活。MCP **不**常驻 worker、不自己 apply |
| **工作记忆** | `context.startup` + 手维护 `recent-focus.md` | startup 现读近期改过的 pack/笔记**标题列表**（仍 Vault，不另起库） |
| **长期记忆** | Proposal → 批 → Git | 不变。经验进 skill/context，仍 HITL |

不做：Inbox 变自动执行队列、Skill 变 DAG 运行器、图谱强制推理链。那些要么和 HITL 打架，要么是假实现。

多 Agent：调度在宿主（谁被叫醒、谁拿哪条 Inbox）。共享状态仍是 Inbox + Vault。本仓不实现「Agent 编排内核」。

---

## 3. 博客与基座切割

现在捆在一起的原因：同一份 Vault、一套部署习惯、一个 GitHub 仓。这在 v0.1 合理，长期会拖控制中心：

- 公开站点要备案、CDN、主题；基座要 loopback、token、审计
- 博客发布节奏 ≠ 记忆协议节奏
- 「个人 AI 工作台」的主入口不该是静态博客

**目标形态**（未开工，切的时候再开 Issue）：

```text
工作台仓（控制中心 + MCP + Vault 协议）     必选
公开博客仓（主题 + Vite 栏目）              可选插件
Vault 仍一份：文章/ 给博客扫描，Workbase/ 给 MCP
```

切割原则：

1. **先逻辑切、后仓库切。** 代码上博客只读 `文章/` `项目/` `友链/`；MCP 继续读全 Vault。目录边界先于拆 repo。
2. **博客降为可选输出。** 没有博客仓，MCP + Vault 仍是完整工作台。有博客仓，就多一个「把 public 打成站点」的构建。
3. **不要做成 DSH 插件才叫切割。** 博客是「展示适配器」，MCP 是「记忆协议」。两边都可以被宿主当 MCP/构建脚本接入，地位不平等：没有博客可以，没有 Vault 不行。
4. **友链、主题、Caddy 站点跟博客走；Token、Proposal、Inbox、agent_prompt 跟基座走。**

v0.1.1 **不拆仓**。拆仓的触发：控制中心 UI 开始和博客 token/构建互相污染，或发版时博客改动总被 MCP 契约带着。

---

## 4. 明确不做（直到有新 Issue 推翻）

- 向量库 / Embedding 当主检索
- 用 Noema / 其它记忆插件替换 Vault
- 用 DSH 重写 MCP
- Agent 绕过 Proposal 写盘
- 为「像控制中心」先做空壳调度 UI
